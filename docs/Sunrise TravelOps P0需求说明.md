# Sunrise TravelOps P0 需求说明

版本：v1.6（同步 2026-09-01 旅行社多联系人、询盘联系人联动与日志边界，版本化目标不变）
日期：2026-09-01
目标：完成从询盘到报价 PDF 的最小可用闭环

> 当前实现说明（2026-09-01）：`sunrise-travel-ops-web` 是使用前端 mock 数据和运行时内存状态的 P0 交互原型。当前已打通旅行社资源与多联系人 → 询盘 → 多个独立行程 → 每日资源成本 → 团费报价 → 中文 PDF 预览与下载的简化链路。本文主体仍是 P0 目标与验收基线；当前完成度、实际计算规则和与目标的差距以第 0 节为准。

### 0.2 当前报价模型

当前前端实现采用“资源成本 + 团费报价”模型，而不是本文件原先描述的“每个 Item 分别维护售价后汇总”：

1. 行程 Item 只保存资源单位成本和总成本，不保存对客单位售价。
2. 酒店房间数根据成人和儿童总人数按双人入住自动计算；酒店 Item 数量会随人数变化同步，不再采集单住人数。
3. 单房差单价按各酒店房型单位成本之和的 50% 计算，仅在报价抽屉中作为可选附加价展示。
4. 基础团成本即资源总成本；成人等效人数为“成人数 + 儿童数 × 70%”，用于展示基础人均成本。
5. 系统按 10% 目标利润率生成建议成人团费；有价格权限的用户手工修改后，以修改值继续计算。儿童团费固定为成人团费的 70%。
6. 当前团体总报价为成人团费与儿童团费之和，不自动叠加单房差；预计利润为总报价减资源总成本，实际利润率为预计利润除以总报价。
7. 报价默认利润率常量当前为 10%，所有未手工设置成人价的行程均根据实时总成本自动更新建议成人价。

### 0.3 当前实现与 P0 目标的关键差距

- 当前代码已经完成可演示的前端闭环，但尚未完成 Costing 和 Quote 版本化，因此不满足第 3 节第 7—9 条以及第 8 节完整验收要求。
- 本版已将第 4.7、4.8 和第 10 节同步为成人团费、儿童 70% 与单房差单价展示模型；后端建模时必须按该口径设计 Quote Line、快照与舍入规则。
- PDF 仅在用户确认下载后更新状态、记录日志与报价生成时间；预览、取消或校验失败不会记录生成成功。当前 PDF 直接从 Itinerary 和实时报价计算生成，并未绑定 Quote Version。
- 当前所有业务数据、日志和权限判断都在前端，刷新后恢复初始 mock 数据；不能作为 P0 生产验收中的持久化、安全或审计证据。
- 旅行社邮箱属于旅行社，联系人只保存姓名和电话，不设置部门；询盘中新增的联系人会立即写入当前旅行社联系人集合，但刷新后恢复初始 mock 数据。
- Costing/Quote 实体与版本快照由后端实现；状态变化、审计日志写入和版本快照必须在同一后端数据库事务内完成。
- 当前前端 PDF 是过渡方案；后续改为后端基于锁定 Quote Version 生成、保存并返回 PDF，记录文件哈希、生成人和可信生成时间，支持历史文件原样下载。
- 前端接入后端前待办：拆分 API 类型与页面 Form 类型、建立统一请求客户端、统一金额和时间契约、固化主链路基线回归。

## 1. P0 产品目标

P0 要交付一套供 Sunrise 内部员工使用的旅游询盘、行程设计与报价系统，完整记录：

```text
Inquiry 询盘
→ Itinerary 独立需求与行程方案
→ Costing 成本核算
→ Quote 报价版本
→ PDF 报价报告
```

系统必须保证关键需求、行程、成本和报价版本可追溯。每份 PDF 必须固定对应一个报价版本，后续修改通过新版本完成，不能覆盖已经生成的报告。

## 2. P0 用户角色

| 角色 | 核心职责 | 询盘权限 |
|---|---|---|
| 系统管理员 | 管理用户、角色、权限、字典、编号和系统配置 | 全部 |
| 资源主管 | 维护资源库报价、价格有效期和淡旺季规则；处理地接社报价变更 | 无 |
| 收客计调 Inquiry Coordinator | 创建询盘、维护客户信息、跟进客户、维护报价版本和生成报价 PDF | 查看列表、新增、修改 |
| 操作计调 | 创建行程、选择资源，并使用资源库价格完成成本核算 | 查看列表、修改 |

收客计调和操作计调同属于计调部，不拆分为两个独立部门；岗位权限通过角色区分。

P0 不包含客户、代理商、地接社、导游和司机的独立登录门户。

## 3. P0 核心业务规则

1. 每笔业务必须从 Inquiry 开始。
2. 一个 Inquiry 可以创建多个相互独立的 Itinerary。
3. 每个 Itinerary 独立保存基础信息、每日路线、观光行程内容和资源方案。
4. 人数、日期、天数或每日方案发生变化时，创建新的 Itinerary。
5. 新 Itinerary 可以复制已有行程，但复制后两者互不影响。
6. Draft 状态下 Itinerary 的所有信息均可修改；行程报价后如需修改，必须复制为新的独立 Itinerary，不能覆盖原行程。
7. Costing 和 Quote 必须版本化。
8. 每份 PDF 报价报告必须绑定一个明确的 Quote Version。
9. PDF 生成后，该 Quote Version 不允许直接覆盖；需要修改时创建新 Quote Version 并重新生成 PDF。
10. P0 只负责生成报价报告，不负责客户确认、订单、执行和财务结算。
11. 所有关键状态、成本、售价、版本生成和 PDF 生成动作必须写入 Audit Log。

## 4. P0 功能范围

### 4.1 用户、认证与权限

- 账号密码登录、退出和当前用户查询。
- 修改密码、管理员重置密码。
- 用户启用和停用。
- 角色管理、权限管理、用户角色分配。
- 权限粒度至少支持模块读取、创建、修改和导出。
- 支持本人、团队和全部数据范围。
- 记录登录成功、失败、IP、客户端和时间。
- 使用安全的管理员初始化流程，不内置弱默认密码。

验收要求：

- 未登录用户不能访问业务 API。
- 无权限用户即使直接调用 API 也会被拒绝。
- 用户被停用后不能继续登录或刷新令牌。

### 4.2 系统配置与字典

- 管理来源渠道、资源类型和询盘状态原因等字典。
- 配置询盘号、行程号、成本核算单号和报价号规则。
- 配置时区和基础系统参数。
- P0 所有成本、售价和报价统一使用人民币，不提供币种或汇率选择。
- 字典值停用后不得影响历史记录显示。

### 4.3 旅行社与询盘 Inquiry

Inquiry 只保存销售机会和客户沟通过程，不保存会随行程方案变化的结构化旅行数据。

核心字段：

- 询盘编号。
- 旅行社资源 ID；创建询盘时必须从旅游资源库中选择已启用的旅行社。
- 旅行社名称和旅行社编号，由所选旅行社资源带出。
- 联系人姓名和电话：联系人从所选旅行社的全部联系人中选取；电话由联系人带出。
- 邮箱：固定使用所选旅行社的统一邮箱，不属于联系人，也不允许在询盘中单独修改。
- 国家或地区，由所选旅行社资源带出。
- 来源渠道。
- 客户原始消息。
- 内部备注。
- 收客计调负责人；创建询盘时非必填，可在后续编辑时分配。
- 操作计调负责人，创建询盘时必填。
- 下一次跟进时间。
- 流失原因。
- 状态、创建人和时间。

状态：

```text
New
Planning
Quoted
Lost
Archived
```

功能要求：

- 系统支持创建、查看、编辑、筛选和归档询盘，各操作按角色权限开放。
- 新建或编辑询盘时从旅游资源库选择旅行社，不允许在询盘中另行维护旅行社名称、编号、统一邮箱和国家/地区。
- 选择旅行社后，联系人只能从该旅行社全部联系人中选择；切换旅行社时清空原联系人，避免保留其他旅行社人员。
- 联系人选择器支持搜索和直接输入姓名创建联系人。新联系人立即同步写入当前旅行社联系人集合，电话初始为空，可在旅行社资源页继续补充。
- 收客计调可以查看询盘列表、新增和修改询盘；操作计调可以查看询盘列表和修改询盘。两个角色均无询盘归档权限。
- 创建询盘时收客计调负责人非必填，操作计调仍为必填；支持后续分配或转移收客计调与操作计调负责人。
- New：已创建、已指定操作计调且尚无行程；收客计调负责人可以暂时为空。
- Planning：至少存在一个 Draft 行程；已报价询盘可以通过创建或复制新的 Draft 行程降级为 Planning。
- Quoted：至少存在一个已报价行程，当前等待客户回复。
- Lost：必须填写流失原因；进入 Lost 后询盘所有字段及其行程均只可查看。
- Archived：归档后询盘所有字段只可查看；进入行程管理时仅可查看已有行程，不可新增、复制、编辑或生成新的报价 PDF。
- 添加跟进记录和附件。
- 一个 Inquiry 可以查看其所有行程和报价版本。
- 不允许物理删除已有业务关联的 Inquiry。

询盘日志与 Draft 保存：

- 询盘列表的“行程”列同时提供“行程管理”和“询盘日志”入口；已归档、已流失询盘仍可查看日志。
- P0 记录七类操作：创建询盘、编辑询盘、创建行程（含复制为新 Draft）、编辑并保存 Draft 行程、确认下载行程 PDF、归档询盘、流失询盘。
- 日志按操作时间倒序展示操作类型、操作时间、操作人姓名和账号；行程类日志展示行程编号和标题，流失日志展示流失原因。
- 取消操作、校验失败或 PDF 仅预览但未确认下载时，不记录成功日志；一次询盘编辑同时进入 Lost 时，分别记录“编辑询盘”和“流失询盘”。
- Draft 行程提供独立“保存”动作。保存更新时间并记录“编辑行程”，但不生成 PDF，也不改变 Draft 状态；当前原型不记录编辑前后 diff。
- 当前日志通过 inquiry-log service 读写前端 mock/内存数据，刷新后恢复初始记录；生产环境必须改为服务端不可变审计。

### 4.4 资源主数据

P0 资源类型：

- 旅行社 Travel Agency。
- 地接社 Ground Operator。
- 酒店 Hotel。
- 房型 Room Type。
- 车辆 Vehicle。
- 司机 Driver。
- 车辆司机绑定 Vehicle-Driver Binding。
- 导游 Guide。
- 餐厅 Restaurant。
- 景点 Attraction。

通用要求：

- 每类资源使用稳定唯一的 `*_code`。
- 支持启用和停用，历史已引用资源不能物理删除。
- 旅行社记录名称、国家或地区、统一邮箱和多个联系人；联系人只包含姓名和电话，不设置部门。
- 旅行社资源页采用左右主从布局：左侧侧边栏选择旅行社，左侧顶部新增旅行社；右侧显示当前旅行社联系人表格，右侧顶部新增联系人。旅行社与联系人分别维护。
- 酒店、餐厅、景点、导游和车辆本身不区分直营或地接社提供；提供方属于资源报价属性，不得维护在资源主数据上。
- 新增或编辑上述资源报价时必须明确“是否由地接社提供”；选择“是”时，该报价必须关联一个确定的地接社，价格列表对该报价展示地接社 Tag；选择“否”时为直营报价。
- 酒店和房型是不同的资源 Item；酒店可维护多个房型，正式报价由“酒店 + 房型 + 价格有效时间段 + 报价来源”确定。
- 同一资源、同一房型和同一有效时间段可以同时存在直营报价及一个或多个地接社报价；每条报价只能关联一个地接社。
- 资源价格只受有效时间段（如淡季、旺季）影响，不以含早/不含早等条件形成价格维度。
- 资源报价及地接社关系由资源主管维护。收客计调和操作计调不能修改资源库报价；车辆 Item 例外，选择车辆后必须展示资源成本价，并允许填写本行程实际车费。资源成本价与手工车费均须保留，变更必须记录审计日志。
- 车辆和司机分别管理，通过有效期绑定关系关联。
- 导游记录语言、证件、擅长领域和基础日价。
- 餐厅记录菜系、人均成本和菜单附件。
- 景点记录票价、建议游览时长和开放时间。

### 4.5 资源数据导入

- 支持 Excel/CSV 导入旅行社、地接社、酒店、房型、车辆、司机、车辆司机绑定、导游、餐厅和景点。
- 使用固定 sheet、表头和稳定 code。
- 每行支持 Import 和 Ignore。
- 支持必填、类型、字典、外键和重复 code 校验。
- 支持 dry-run，正式导入前显示新增、更新、忽略和失败数量。
- 生成包含 sheet、行号、字段、原值和错误原因的报告。
- 相同文件重复执行不得创建重复资源。
- 导入动作必须记录操作人和结果。

### 4.6 行程 Itinerary

每个 Itinerary 是一套完全独立的行程与报价方案。

顶级字段：

- 行程编号和标题。
- 所属 Inquiry。
- 出行开始和结束日期。
- 天数。
- 成人和儿童人数构成；不采集单住人数。
- 操作计调负责人。
- 状态、创建人和时间。

状态：

```text
Draft
Internal Review
Ready for Costing
Quoted
Archived
```

行程结构：

```text
Itinerary
└── Itinerary Day
    └── Itinerary Item
```

Day 字段：日期、天数序号、出发地、目的地、交通方式和可选观光行程内容。Day 不维护独立的当日主题、用餐摘要或住宿摘要；酒店、餐饮和景点等信息由所选资源 Item 表达。当前编辑界面可录入路线、交通方式、description，并选择资源。

Item 类型至少支持：

```text
hotel
room_type
vehicle
driver
guide
restaurant
attraction
ticket
meal
train
flight
service_fee
other
```

Item 字段：

- 所属 Day。
- 资源类型和资源 ID。
- 选中的资源报价 ID；报价自身记录直营或地接社来源，若为地接社报价，其地接社不允许在行程中另行替换。
- 日期和时间。
- 描述。
- 数量和单位；默认计价单位为酒店 1 间夜、景点 1 人次、车辆 1 辆/天、餐厅按人计价 1 人/餐或整桌计价 1 桌、导游 1 人/天。
- 从资源库报价带出的预计单位成本和总成本；车辆同时记录资源参考成本价和允许手工填写的本行程实际车费，车辆总成本按实际车费计算。
- 价格来源；金额统一为人民币。
- 选择人和备注。

功能要求：

- 创建和编辑 Draft 行程。
- 增加、编辑、删除和排序 Day 与 Item。
- 复制完整行程、复制某一天。
- 复制生成的数据与来源行程完全独立。
- 可以在审计日志记录复制来源，但不建立实时数据依赖。
- Draft 状态下所有行程信息均可修改；行程报价后禁止覆盖，调整时必须复制为新的独立 Itinerary。

### 4.7 成本核算 Costing

- 从 Itinerary Item 快照生成新的 Costing Sheet。
- 一个 Itinerary 可以生成多个 Costing Sheet 版本。
- Costing Line 保留来源 Itinerary Item ID 和生成时快照。
- 支持数量 × 单价计算；金额统一使用人民币，不进行汇率换算。
- 自动计算各 Item 总成本和行程资源总成本。
- 每一个 Itinerary Item 可独立设置数量和单位；除车辆外，成本价格必须来自资源库报价且不得手工覆盖。车辆选择后展示资源参考成本价，并允许操作计调填写本行程实际车费；由地接社提供时仍使用报价中已确定的地接社，直营时不关联地接社。
- 酒店与房型分别作为资源 Item 管理，但成本核算和报价以“酒店 + 房型”对应的一条具体价格计算。
- P0 不提供针对非车辆行程 Item 临时增加或减少资源报价的常规功能；车辆手工车费是明确的业务例外。
- 儿童价和单房差使用报价专用计算规则，不作为 `other` Item。免费名额、税费和服务费当前未建立专用模型；后续如允许新增临时费用行，必须填写来源和原因。
- Costing 状态：Draft、Ready、Locked、Archived。
- Costing 生成 Quote Version 后必须锁定。
- 内部成本不能出现在客户可见文档中。

### 4.8 报价 Quote

数据结构：

```text
Quote
└── Quote Version
    └── Quote Line
```

功能要求：

- 从已完成的 Costing Sheet 创建 Quote Version。
- 一个 Quote 可以有多个 Quote Version。
- Quote Line 类型为成人团费和儿童团费；单房差作为独立的可选附加价展示，不按每个资源 Item 形成逐项对客售价。
- 酒店房间数根据成人和儿童总人数按双人入住计算；不采集单住人数。单房差单价为各酒店房型单位成本之和的 50%，报价抽屉仅展示该单价。
- 基础团成本为资源总成本；基础人均成本按“成人数 + 儿童数 × 70%”计算。
- 成人团费由有价格权限的用户填写；儿童团费为成人团费的 70%。当前团体总报价为成人团费与儿童团费之和，不自动叠加单房差；预计利润为总报价减资源总成本，实际利润率为预计利润除以总报价。
- 记录总成本、总售价、毛利、毛利率、人均价、人民币标识、客户可见备注和内部备注。
- 每次价格或对客内容实质变化必须创建新版本。
- 从指定 Quote Version 生成中文或英文报价 PDF。
- PDF 必须包含报价编号、版本号、生成时间、旅行社信息、人数、行程日期、人民币总价、人均价、有效期和客户可见备注；行程安排按 `D / DEPART. / T / SIGHT-SEEING REGION / HOTEL / M` 展示日期、路线、交通方式、每日 description、酒店及 `B/L/D` 餐食代码，不输出逐资源内部成本。行程表逐日连续排版，仅当下一行无法放入当前页时分页，并在新页重复表头；不得按固定天数分组产生可继续排版的大块空白。P0 暂不输出团队标准和独立酒店搭配表。
- PDF 不得包含内部成本、加价规则、毛利润、毛利率和内部备注。
- 保存 PDF 文件、文件哈希、生成时间和生成人，并保持历史版本可下载。
- PDF 生成后锁定对应 Quote Version；如需调整，创建新的 Quote Version。
- 支持重新下载同一版本的原 PDF，不允许重新计算后覆盖旧文件。

状态：

```text
Draft
Ready
PDF Generated
Archived
```

### 4.9 审计日志与附件

- Audit Log 记录实体、动作、旧值、新值、操作人、角色、原因、时间、IP 和请求 ID。
- 必须记录状态变化、成本和售价变化、行程复制、成本版本生成、报价版本生成、PDF 生成、权限修改、导入和导出。
- 审计日志只能追加，普通用户不能修改或删除。
- 支持从 Quote Version 追溯到 Costing Sheet、Costing Line、Itinerary 和 Itinerary Item。
- 附件支持客户原始资料、行程素材和报价 PDF。
- 附件需要记录业务归属、上传人、时间、类型、大小和访问权限。

### 4.10 岗位工作台

收客计调工作台：

- 新询盘、待跟进和超期跟进。
- 待制作报价和已生成 PDF 的报价。
- 询盘数量、报价数量和 Lost 原因。

操作计调工作台：

## 7. P0 非功能要求

- 部署后自动健康检查，失败时支持回滚。
- 开发、测试和生产环境配置隔离。

### 7.4 工程质量

- 前端统一使用 pnpm 和唯一锁文件。
- 数据库结构使用迁移工具管理。
- 权限、状态机、金额计算、导入和核心 API 必须有自动化测试。
- 从询盘到生成报价 PDF 的完整流程必须有端到端测试。

## 8. P0 验收场景

使用虚构数据完成以下完整流程：

1. 资源主管创建一个旅行社，设置统一邮箱，并通过右侧联系人表格添加多位仅含姓名和电话的联系人。
2. 收客计调创建一条来自 WhatsApp 的云南询盘，选择该旅行社和其中一位联系人；邮箱固定使用旅行社邮箱。
3. 在联系人下拉中直接新增一位人员，确认该人员立即出现在当前旅行社联系人表格中。
4. 操作计调基于 6 人、7 天需求创建三个彼此独立的行程。
5. 客户改为 8 人、10 天后，复制一个已有行程创建新行程，原三个行程不发生变化。
6. 为新行程创建每天的酒店、车辆、导游、景点和餐厅资源项，并独立保存 Draft；保存不生成 PDF、不改变状态。
7. 从行程生成成本单，按各 Item 选中的具体报价记录带出资源库价格；地接社报价同时带出已确定的地接社，并完成资源总成本核算。
8. 填写成人团费，由系统计算儿童团费、单房差单价、团体总报价、预计利润和实际利润率；创建第一版报价并生成行程报价 PDF，PDF 不包含内部成本和毛利信息。
9. 修改成人团费或其他对客内容时创建第二个 Quote Version 并生成新的 PDF，第一版 PDF 仍可原样下载。
10. 从 Quote Version 可以追溯到成本单、行程和资源项。
11. 审计日志展示所有关键动作的操作人、时间、旧值、新值和原因；前端原型至少正确展示七类询盘关联日志。

以上场景全部通过，才视为 P0 业务闭环完成。

## 10. 已确认的业务决策

1. 客户主体只支持旅行社，不支持个人客户。旅行社作为旅游资源主数据维护；询盘必须关联已启用的旅行社，并从资源库带出其编号、名称和联系信息。
2. P0 不执行线上收付款，也不包含收付款结果记录；如后续增加财务功能，只记录线下收付款结果。
3. 系统只使用人民币。成本、售价、报价和报表均以人民币存储和展示，不提供币种选择、汇率获取、换算或锁定。
4. 每一个 Itinerary Item 均可独立设置数量和单位，单位成本从资源库报价带出并汇总为内部资源成本；车辆 Item 同时显示资源参考成本价，并允许填写本行程实际车费。P0 不在 Item 上维护对客售价。
5. 儿童团费固定为成人团费的 70%；单房差单价按各酒店房型单位成本之和的 50% 计算，仅作为可选附加价展示，不采集单住人数，也不自动计入当前团体总报价。免费名额、税费和服务费暂不建立专用模型。
6. P0 不设计成本差异或售价差异的审批规则与阈值。
7. P0 不定义收客计调查看完整成本和毛利的特殊规则；不得据此扩展审批或财务权限。开发权限矩阵时仅按完成当前岗位任务所需的最小权限配置。
8. 客户最终得到的是指定 Quote Version 生成的行程报价 PDF。P0 不保存客户确认、签字或其他确认凭证。
9. P0 不处理订单取消、部分取消、退款和坏账。
10. 后端 API 全部重新设计，不兼容现有 API；以前后端共同确认的新 OpenAPI 契约为准。
11. 不迁移历史数据，也不导入历史未完成订单；新系统以空业务库开始使用。资源主数据仍可通过标准导入模板初始化。
12. 酒店、餐厅、景点、导游和车辆本身不记录是否由地接社提供；该字段属于每一条资源报价，价格列表对地接社报价展示 Tag。
13. 酒店和房型是不同的资源 Item，正式报价由“酒店 + 房型 + 价格有效时间段 + 报价来源”确定；同一房型可同时存在直营报价和多个地接社报价，每条报价最多关联一个地接社。
14. 资源报价只受时间段（如淡季、旺季）影响，不考虑含早/不含早等其他报价维度。
15. 添加资源报价时即确定报价来源；若由地接社提供，同时确定地接社。行程必须选择具体报价记录，不得只选择资源后另行指定价格或地接社。
16. 仅资源主管可以维护资源库报价。收客计调和操作计调不得修改资源库价格；车辆 Item 的实际车费允许在所选车辆资源成本价基础上手工填写，并必须保留参考成本价及变更审计。地接社报价变化时仍由资源主管修改并留下审计记录。
17. Draft 行程的所有信息均可修改；行程报价后如需调整，必须复制为新的独立 Itinerary。
18. 默认计价单位为：酒店 1 间夜、景点 1 人次、车辆 1 辆/天、餐厅按人计价 1 人/餐或整桌计价 1 桌、导游 1 人/天。
19. 金额统一保留两位小数；除车辆实际车费外，P0 不提供针对单个行程 Item 临时增减资源报价的常规功能。
20. 创建询盘时收客计调负责人非必填，操作计调必须指定；询盘业务状态为 New、Planning、Quoted、Lost，Archived 作为归档状态。
21. Lost 询盘只可查看；Archived 询盘及其已有行程只可查看，行程管理中不得新增、复制、编辑行程或生成新的报价 PDF。
22. 一个旅行社维护一个统一邮箱和多个联系人；联系人只保存姓名和电话，不设置部门。旅行社与联系人在左右主从页面中分别维护。
23. 询盘联系人从所选旅行社全部联系人中选择；联系人列表没有目标人员时可直接新增并同步回旅行社，询盘邮箱始终固定使用旅行社邮箱。
24. Draft 行程保存、PDF 确认下载和七类询盘关联操作分别记录明确日志；生产环境由后端在业务事务成功后写入不可变审计记录。

## 11. 仍待确认的文档输出事项

以下事项只影响 PDF 样式和语言，不改变 P0 核心数据模型：

2. PDF 需要中文、英文分别生成，还是还要提供中英双语版。
3. 真实完整业务案例及现有报价单样例（待业务方后续提供）。
