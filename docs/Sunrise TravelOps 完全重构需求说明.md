# Sunrise TravelOps 完全重构需求说明

版本：v1.6（同步 2026-09-01 旅行社多联系人、询盘联系人联动与日志边界，目标路线图不变）
日期：2026-09-01
用途：作为产品范围确认、系统设计、任务拆分和验收的统一基线

> 当前实现说明（2026-09-01）：`sunrise-travel-ops-web` 是使用前端 mock 数据和运行时内存状态的 P0 交互原型。当前已打通旅行社资源与多联系人 → 询盘 → 多个独立行程 → 每日资源成本 → 团费报价 → 中文 PDF 预览与下载的简化链路。本文主体仍描述完整目标需求；当前完成度、实际计算规则及已知差距以第 0 节为准。

### 0.2 当前报价计算规则

当前原型不再为每个行程资源 Item 维护对客售价。Item 只保存资源报价带出的单位成本和总成本；报价抽屉按以下规则计算：

1. 酒店入住人数为成人数加儿童数；房间数按双人入住计算，不再采集单住人数。
2. 单房差单价为行程各酒店房型单位成本之和的 50%，仅在报价抽屉中作为可选附加价展示。
3. 基础团成本为资源总成本；成人等效人数为“成人数 + 儿童数 × 70%”。
4. 系统按总报价达到 10% 目标利润率自动生成建议成人团费；有价格权限的用户手工修改后，以修改值继续计算。
5. 儿童团费固定为成人团费的 70%；单房差仅展示单价，不自动计入当前团体总报价。
6. 当前团体总报价为成人团费与儿童团费之和；预计利润为总报价减资源总成本，实际利润率为预计利润除以总报价。
7. `DEFAULT_QUOTE_PROFIT_MARGIN_RATE` 当前为 10，所有未手工设置成人价的行程均根据实时总成本自动更新建议成人价。

### 0.3 与目标需求的关系

- 第 4 节以后仍是产品目标和后续建设基线，不代表上述未实现能力已经存在。
- 本版已将 P0 报价正文同步为成人团费、儿童 70% 和单房差单价展示模型；后端实现必须复核公式、快照字段和舍入规则，不能继续沿用旧的逐 Item 对客售价口径。
- Costing Sheet、Quote Version、PDF 历史文件、服务端不可变审计、导入、附件、完整资源类型、后端鉴权、订单、执行、变更和结算仍属于未完成目标，不应从路线图中删除。状态变更、审计日志和版本快照必须由后端在同一数据库事务内完成。
- 当前前端 PDF 记录报价生成时间只是过渡方案；后续改为后端基于锁定 Quote Version 生成并保存 PDF，记录文件哈希、生成人和可信生成时间，支持历史文件原样下载。
- 当前旅行社邮箱属于旅行社，联系人只保存姓名和电话，不设置部门；询盘中新增联系人会立即写入当前旅行社联系人集合，但刷新后恢复初始 mock 数据。
- 前端接入后端前仍需拆分 API 类型与页面 Form 类型、建立统一请求客户端、统一金额和时间契约，并固化现有主链路基线回归。
- 当前代码已经提供清晰的 mock service、领域类型、金额工具和行程组合式函数边界，可作为后端接入时的前端替换点，但不能直接充当生产数据与安全边界。

## 1. 文档结论

Sunrise TravelOps 应重构为一套面向旅游定制业务的“订单全生命周期与成本追溯系统”，核心不是资源资料录入，也不是面向游客的电商网站，而是完整记录：

> 客户从哪里来、提出了什么需求、行程如何设计、成本如何形成、客户确认了哪个报价、订单如何执行、地接社最终确认了什么价格、发生了哪些变更、最终结算为何与原报价不同。

系统必须以业务链路和历史证据为中心，确保任何关键价格、客户确认结果、订单基准和结算差异都可以追溯到具体资源项、版本、人员、时间和原因。

建议把需求划分为三层：

1. **核心 ERP**：本次完全重构的主范围，优先实现内部员工使用的端到端业务闭环。
2. **协同扩展**：客户、代理商、地接社、导游和司机的外部门户、消息通知、评价和支付协同。
3. **平台化远期能力**：分销、内容营销、团购、签证、保险、邮轮等，不应进入核心 ERP 首版。

## 3. 产品目标

### 3.1 核心目标

- 打通 Inquiry → Itinerary → Costing → Quote → Order → Operation → Change Order → Settlement 全链路。
- 建立统一资源主数据，供行程、报价、执行和结算复用。
- 对需求、行程、成本和报价实行版本管理。
- 客户确认后的报价与订单基准不可被无痕覆盖。
- 对订单执行中的资源、数量、日期、成本和售价变化使用正式变更单。
- 逐项对比报价成本、地接社确认成本、变更影响和实际结算成本。
- 所有关键动作进入统一审计日志。
- 为收客计调、操作计调、财务和管理层提供岗位化工作台与报表。

### 3.2 成功标准

系统上线后必须能准确回答：

- 客户来源、负责人和原始咨询内容是什么？
- 当前行程记录了哪些人数、日期、每日路线、交通方式、观光内容和资源？
- 客户改变需求后创建了哪些独立的新行程？
- 每天安排了哪些资源，每项预计成本和售价是多少？
- 成本单和报价版本是如何计算出来的？
- 客户最终确认的是哪个报价版本，何时确认，由谁记录？
- 订单执行时哪些资源已经确认，地接社确认价格是多少？
- 订单确认后发生过哪些变更，谁申请、谁审批、客户是否确认？
- 实际结算比报价成本增加或减少多少，原因和责任环节是什么？
- 最终收入、成本、毛利和毛利率是多少？

## 4. 产品范围

### 4.1 P0：询盘、行程与报价首版

- 身份认证、用户、角色、权限。
- 系统字典、编号规则和基础配置。
- 旅行社、地接社与旅游资源主数据。
- Excel/CSV 资源导入、校验和错误报告。
- 旅行社、联系人与询盘管理。
- 询盘原始需求、跟进记录，以及包含完整需求快照的独立行程方案。
- 行程方案、行程天和行程资源项。
- 成本核算、加价和利润计算。
- 报价单、报价版本和版本锁定。
- 从报价版本生成中文或英文 PDF 报价报告，并保留历史文件。
- 询盘、行程、成本、报价与 PDF 生成的基础审计日志。
- 收客计调和操作计调的基础工作台。
- API 健康检查、API 文档、监控、备份和恢复。

### 4.2 P1：订单执行、财务与协同扩展

- 客户确认报价和确认凭证。
- 正式订单与订单明细快照。
- 操作计调执行任务与地接社确认。
- 订单变更、内部审批与客户确认。
- 客户收款、地接社付款的线下结果记录和逐项结算；不在系统内执行真实资金交易。
- 全链路审计、经营报表和差异下钻。
- 旅行社/代理商门户：提交询价、确认报价、上传团员资料、查看行程和服务人员。
- 地接社门户：维护产品、接收订单、确认资源与价格、上传凭证。
- 导游移动端：查看任务、提交接送机、用餐、住宿、日报和凭证。
- 司机移动端：查看任务、提交接送机和服务凭证。
- 微信、短信、邮件或 WhatsApp 通知。
- 报价单、行程确认单、车辆调拨单、导游调拨单、地接确认单等文档生成。
- 服务评价、地接社评分和质量管理。
- 更完整的应收、应付、线下收付款结果记录和对账能力，不包含付款发起。

### 4.3 P2：平台化远期需求

下列内容来自早期功能表，与内部 ERP 的目标不同，建议单独立项：

- 游客在线浏览、预订和支付。
- 导游打赏、司机/导游提现。
- 微信公众号完整交易闭环。
- 三级分销、佣金和分销商提现。
- 攻略、相册、问答、游记、资讯和结伴等内容平台。
- 团购、签证、保险、户外活动、邮轮等独立产品商城。

## 5. 用户与角色

### 5.1 内部角色

| 角色 | 核心职责 | 关键数据权限 |
|---|---|---|
| 系统管理员 Admin | 用户、角色、权限、字典、编号、系统配置 | 全局管理；不应默认拥有财务审批权 |
| 资源主管 Resource Manager | 维护资源库报价、价格有效期和淡旺季规则；处理地接社报价变更 | 独占资源库报价新增、修改和停用权限；价格变更必须审计 |
| 收客计调 Inquiry Coordinator | 创建询盘、整理旅行社及联系人信息、维护报价、跟进成交 | 询盘权限仅包含查看列表、新增和修改；无询盘归档权限。P0 不定义完整成本和毛利查看权限 |
| 操作计调 Operations Coordinator | 设计行程、选择资源、核算成本、执行预订、记录地接社确认、发起变更 | 询盘权限仅包含查看列表和修改；无询盘新增、归档权限 |
| 财务 Finance | 收款、付款、结算、差异核对、利润确认 | 财务全量数据；不能修改客户确认报价基准 |
| 主管/审批人 Manager | 审批成本异常和变更、查看跨团队经营数据 | 跨团队只读与指定审批权限 |
| 管理层 Boss | 查看经营、利润、效率、偏差和风险 | 汇总只读，必要时可下钻审计链路 |

收客计调和操作计调同属于计调部，不拆分为两个独立部门；岗位权限通过角色区分。

### 5.2 外部角色（P1）

- 旅行社/代理商用户。
- 地接社用户。
- 导游。
- 司机。

外部账号必须与内部账号隔离权限域。外部用户只能访问明确属于自身组织、订单或任务的数据。

### 5.3 权限原则

- 使用 RBAC，权限粒度至少为“模块 + 动作”。
- 支持数据范围：本人、团队、部门、全部。
- 读取成本、修改价格、确认客户报价、审批变更、审批结算必须分离。
- 收客计调和操作计调无权修改资源库报价；该权限仅授予资源主管。车辆 Item 例外：选择车辆后展示资源成本价，并允许填写本行程实际车费，参考价和手工值都必须进入审计与快照。
- 禁止仅依赖前端隐藏按钮；后端对每次读写进行权限检查。
- 敏感导出、批量导入、审批、锁定和解锁操作必须审计。

## 6. 核心业务链路

```text
旅行社/代理商咨询
  → Inquiry 询盘
  → Itinerary 独立需求与行程方案
  → Itinerary Day / Item 每日安排与资源项
  → Costing Sheet / Line 成本核算版本
  → Quote / Quote Version / Line 客户报价版本
  → 客户确认并锁定
  → Order / Order Line 固化订单基准
  → Operation Task 操作计调执行任务
  → Ground Operator Confirmation 地接社确认
  → Change Order 订单后变更
  → Settlement / Line 逐项结算
  → 收付款完成、差异分析、关闭归档
```

不得绕过的约束：

- 每单必须有 Inquiry 作为业务源头。
- 每个 Itinerary 必须自身保存基础信息、每日路线、观光内容和资源方案，不能依赖 Inquiry 中会继续变化的字段。
- 客户在成交前改变人数、日期、天数或每日方案时，应创建新的独立 Itinerary；可复制已有行程作为初始数据，但复制后两者互不影响。
- 报价必须从 Costing Sheet 版本生成。
- Order 必须从已确认并锁定的 Quote Version 创建。
- 客户确认后的报价、订单价格基准不得直接修改。
- 订单确认后对资源、日期、数量、成本或售价的修改必须走 Change Order。
- Settlement 必须按 Order Line/资源项逐条生成，不能只录总金额。

## 7. 核心领域对象与关系

```text
TravelAgency
  ├─ TravelAgencyContact
  └─ Inquiry
      ├─ Itinerary
      │   └─ ItineraryDay
      │       └─ ItineraryItem
      │           ├─ CostingLine
      │           ├─ OrderLine
      │           ├─ OperationTask
      │           ├─ GroundOperatorConfirmation
      │           ├─ ChangeOrderLine
      │           └─ SettlementLine
      └─ Quote
          └─ QuoteVersion
              └─ QuoteLine
                  └─ Order
                      └─ OrderLine
```

所有业务实体应具备统一元数据：唯一 ID、业务编号、状态、创建人、创建时间、修改人、修改时间、版本号或乐观锁字段；需要归档的实体使用软删除或归档状态，不直接物理删除。

## 8. 功能需求

### 8.1 身份认证与系统管理

- FR-AUTH-001：账号密码登录、退出、当前用户查询和密码修改。
- FR-AUTH-002：支持用户启用、停用、密码重置和登录失败保护。
- FR-AUTH-003：支持角色和权限配置，一个用户可拥有多个角色。
- FR-AUTH-004：记录登录成功、失败、IP、客户端和时间。
- FR-SYS-001：管理渠道、资源类型、差异原因、状态原因等业务字典。
- FR-SYS-002：配置业务编号规则，例如询盘号、报价号、订单号、变更单号和结算单号。
- FR-SYS-003：配置时区和基础系统参数。系统金额固定使用人民币，P0 不配置差异审批阈值。
- FR-SYS-004：管理员初始化必须通过安全命令或一次性流程完成，不内置弱默认密码。

### 8.2 旅行社、联系人与询盘 Inquiry

- 客户主体只支持旅行社，不支持个人客户；旅行社作为旅游资源主数据维护。创建或编辑 Inquiry 时必须从资源库选择已启用的旅行社，不允许在 Inquiry 中另行维护旅行社资料。
- 一个旅行社维护一个统一邮箱和多个联系人；联系人只包含姓名和电话，不设置部门、职位或其他组织分组。
- Inquiry 记录旅行社资源 ID 和联系人引用，并从所选旅行社带出编号、名称、统一邮箱和国家/地区，从联系人带出姓名和电话；Inquiry 自身记录来源渠道、客户原始消息、内部备注、计划天数、下次跟进时间、收客计调负责人和操作计调负责人。联系人 WhatsApp 不属于 Inquiry 字段。创建 Inquiry 时收客计调负责人非必填，操作计调负责人仍为必填。出行日期、人数、每日路线、交通方式和资源属于 Itinerary，不在 Inquiry 重复维护。
- 选择旅行社后，联系人只能从该旅行社全部联系人中选择；切换旅行社时必须清空原联系人。联系人选择器支持搜索和直接输入姓名新增联系人，新联系人同步写入当前旅行社联系人集合，电话可后续补充。
- Inquiry 邮箱始终取所选旅行社统一邮箱，不随联系人切换，也不允许在 Inquiry 中单独覆盖。
- 来源渠道至少支持 Website、Email、WhatsApp、TikTok、Facebook、Referral 和 Other，并允许字典扩展。
- P0 询盘业务状态：New、Planning、Quoted、Lost，Archived 作为归档状态；P0 不使用 Qualified、Negotiating 或 Won。
- New：询盘已创建、已指定操作计调且尚无行程；收客计调负责人可以暂时为空。
- Planning：询盘至少存在一个 Draft 行程；已报价询盘创建或复制新的 Draft 行程时可以降级为 Planning。
- Quoted：至少存在一个已报价行程，当前等待客户回复。
- Lost：必须填写流失原因；进入 Lost 后询盘所有字段及其行程均只可查看，不可再新增或编辑。
- Archived：归档后询盘所有字段只可查看；进入行程管理时仅可查看已有行程，不可新增、复制、编辑或生成新的报价 PDF。
- 删除应优先改为 Archived。
- 收客计调可以查看询盘列表、新增和修改询盘；操作计调可以查看询盘列表和修改询盘。两个角色均无询盘归档权限。
- 支持负责人分配、跟进记录、下一次跟进时间和附件。
- 一个 Inquiry 可关联多个彼此独立的行程方案和报价。
- 询盘列表的“行程”列同时提供“行程管理”和“询盘日志”入口；已归档、已流失询盘仍可查看日志。

### 8.3 询盘需求与行程创建

- Inquiry 保存客户最初的原话、来源、联系人、收客计调负责人、操作计调负责人和持续跟进记录，不承担行程版本管理。
- 创建 Itinerary 时填写标题、出行日期、天数、成人数和儿童数；不采集单住人数，也不维护酒店等级、房型偏好、交通偏好、导游需求、行程节奏、餐饮要求、预算、特殊要求或收客计调备注。
- 人数、日期、天数或每日方案不同的方案，在系统中都是不同的 Itinerary。
- 客户提出新需求时创建新的 Itinerary，不修改已有 Itinerary；已有行程、成本和报价保持原样。
- 新行程可以从任意已有行程复制基础信息、Day 和 Item。复制仅生成初始数据，之后双方没有实时关联、级联更新或共享可变数据。
- 系统可以在审计日志中记录“从哪个行程复制”，但该信息只用于追溯，不构成业务依赖。
- Draft 状态下 Itinerary 的所有信息均可修改；行程报价后如需调整，必须复制为新的独立 Itinerary，原行程保持不变。
- Draft 行程支持独立保存。每次明确保存都更新时间并记录“编辑行程”，但不生成 PDF，也不改变 Draft 状态。

### 8.4 资源主数据

资源类别：

- Travel Agency 旅行社。
- Ground Operator 地接社。
- Hotel 酒店。
- Room Type 房型。
- Vehicle 车辆。
- Driver 司机。
- Vehicle-Driver Binding 车辆司机绑定。
- Guide 导游。
- Restaurant 餐厅。
- Attraction 景点。
- 后续可扩展 Ticket、Train、Flight、Meal、Service Fee 和 Other。

通用要求：

- 每类资源使用稳定唯一的 `*_code`，名称不能作为唯一关联键。
- 支持启用/停用，历史订单引用的资源不可物理删除。
- 旅行社记录名称、国家或地区、统一邮箱和多个联系人；联系人只保存姓名和电话，不设置部门。Inquiry 使用旅行社与联系人稳定 ID 建立关联。
- 旅行社维护页采用左右主从布局：左侧侧边栏选择旅行社并在顶部新增旅行社；右侧显示当前旅行社联系人表格并在顶部新增联系人。旅行社与联系人分别维护。
- 酒店、餐厅、景点、导游和车辆本身不区分直营或地接社提供；提供方属于资源报价属性，不得维护在资源主数据上。
- 新增或编辑上述资源报价时必须明确“是否由地接社提供”；选择“是”时，该报价必须关联一个确定的地接社，价格列表对该报价展示地接社 Tag；选择“否”时为直营报价。
- 酒店和房型是不同的资源 Item；酒店可维护多个房型，正式报价由“酒店 + 房型 + 价格有效时间段 + 报价来源”确定。
- 同一资源、同一房型和同一有效时间段可以同时存在直营报价及一个或多个地接社报价；每条报价只能关联一个地接社。资源价格只受淡季、旺季等有效时间段影响，不以含早/不含早等条件形成价格维度。
- 添加资源报价时必须确定报价来源；若由地接社提供，同时确定地接社。行程必须选择具体报价记录，不得只选择资源后另行指定价格或地接社。
- 仅资源主管可以维护资源库报价；收客计调和操作计调不得修改资源库价格。车辆 Item 允许基于所选车辆的资源成本价手工填写本行程实际车费，但不得反向修改资源主数据。
- 车辆和司机为独立实体，使用有效期绑定关系，不能仅存固定的一对一字段。
- 导游支持语言、证件、擅长领域和基础日价。
- 景点支持票价、建议游览时长和开放时间。
- 餐厅支持菜系、人均成本和菜单/附件。

### 8.5 行程 Itinerary

- 一个 Inquiry 可以创建任意多个独立 Itinerary，每个 Itinerary 都代表一套完整需求与方案。
- Itinerary 记录标题、出行日期、天数、成人数、儿童数、状态和操作计调负责人；不记录单住人数、酒店/交通偏好、导游需求、预算、特殊要求或内部需求备注。
- P0 状态：Draft、Internal Review、Ready for Costing/Quote、Quoted、Archived；P0 不使用 Customer Selected。
- 行程包含多个 Itinerary Day；每天包含多个 Itinerary Item。
- Day 记录日期、天数序号、出发地、目的地、交通方式和可选观光行程内容；不记录独立的当日主题、用餐摘要或住宿摘要。酒店、餐饮和景点等信息由资源 Item 表达；当前编辑界面可录入路线、交通方式、description，并选择资源。
- Item 类型包括 hotel、room_type、vehicle、driver、guide、restaurant、attraction、ticket、meal、train、flight、service_fee、other。
- Item 记录资源、选中的资源报价 ID、由报价确定的地接社（仅地接社报价）、日期/时间、数量、单位、资源库单位成本、总成本、价格来源和选择人；金额固定为人民币并保留两位小数。车辆 Item 另外保存资源参考成本价和本行程实际车费，总成本按实际车费计算。P0 对客售价不下沉到每个资源 Item。
- 默认计价单位为：酒店 1 间夜、景点 1 人次、车辆 1 辆/天、餐厅按人计价 1 人/餐或整桌计价 1 桌、导游 1 人/天。
- 支持复制方案、复制某天、调整日期、排序和按天展示。
- Draft 状态下所有行程信息均可修改；行程报价后禁止直接覆盖，调整时必须复制为新的独立行程；订单确认后调整必须走变更单。
- 关键资源必须拆成 Item，不能只写在描述中。

### 8.6 成本核算 Costing

- 从 Itinerary Item 快照生成新的 Costing Sheet，不向已有成本单静默追加或覆盖。
- 一个行程版本可拥有多个成本核算版本。
- Costing Line 保留来源 Itinerary Item ID 和快照。
- 金额固定为人民币，不进行汇率换算；自动计算各 Item 总成本与行程资源总成本。
- 每一个 Itinerary Item 可独立设置数量和单位；除车辆外，单位成本必须使用资源库报价且不得手工覆盖。车辆选择后显示资源参考成本价，并允许填写本行程实际车费；由地接社提供时仍使用报价中已确定的地接社，直营时不关联地接社。
- 酒店和房型分别作为资源 Item 管理，但成本核算和报价以“酒店 + 房型”对应的一条具体价格计算。
- 不提供针对非车辆行程 Item 临时增加或减少资源报价的常规功能；车辆手工车费是明确的业务例外。
- 儿童价和单房差使用报价专用计算规则，不作为 `other` Item。免费名额、税费和服务费当前未建立专用模型；后续如新增额外费用行，必须注明来源和原因。
- 状态至少包括 Draft、Ready、Locked、Archived。
- 一旦生成 Quote Version，来源成本版本必须锁定。
- 成本信息为内部数据，默认不得出现在客户文档和外部接口中。

### 8.7 报价 Quote

- Quote 是报价主题；Quote Version 是每次对客价格版本；Quote Line 是报价明细快照。
- 从已完成的 Costing Sheet 生成 Quote Version，保留来源成本和行程关系。
- P0 Quote Line 类型为成人团费和儿童团费；单房差作为独立的可选附加价展示。资源 Item 仅提供成本与行程内容，不直接形成逐资源对客售价行。
- 酒店房间数按成人和儿童总人数双人入住计算，不采集单住人数；单房差单价为各酒店房型单位成本之和的 50%。基础团成本为资源总成本，基础人均成本按“成人数 + 儿童数 × 70%”计算。
- 成人团费允许有价格权限的用户填写；儿童团费为成人团费的 70%；当前团体总报价为成人团费与儿童团费之和，不自动叠加单房差。预计利润为总报价减资源总成本，实际利润率为预计利润除以总报价。
- 每次价格或客户可见内容发生实质变化必须创建新版本。
- 记录总成本、总售价、毛利、毛利率、人均价、人民币标识、客户可见备注、内部备注和创建人。
- P0 状态：Draft、Ready、PDF Generated、Archived。
- 支持从指定 Quote Version 生成中文或英文行程报价 PDF；PDF 是 P0 的最终客户交付物。
- PDF 行程安排按 `D / DEPART. / T / SIGHT-SEEING REGION / HOTEL / M` 展示日期、路线、交通方式、每日 description、酒店及 `B/L/D` 餐食代码，不输出逐资源内部成本；表格逐日连续排版，仅当下一行无法放入当前页时分页，并在新页重复表头，不得按固定天数分组产生可继续排版的大块空白。P0 暂不输出团队标准和独立酒店搭配表。后端应为餐食代码建立显式字段或结构化餐食明细，不能依赖前端从文本推导。
- PDF 生成后锁定对应 Quote Version，保存原文件、文件哈希、生成时间和生成人，禁止重新计算后覆盖旧文件。
- P0 不保存客户确认、签字或其他确认凭证；客户确认与由报价创建订单属于 P1。

### 8.8 订单 Order

> 本节以及 8.9—8.12 均为 P1 及后续路线图，不属于 P0 验收范围。P0 到生成并保存报价 PDF 为止。

- P1 需要先为 Quote Version 补充客户确认状态、确认人、确认时间、确认方式和证据，再允许创建 Order。

- Order 从确认的 Quote Version 创建，复制 Quote Line 成为不可变的 Order Line 基准快照。
- 保留 `OrderLine → QuoteLine → CostingLine → ItineraryItem` 的完整来源链。
- 记录旅行社、联系人、收客计调负责人、操作计调负责人、确认售价、确认成本基准；金额固定为人民币。
- 状态：Confirmed、Operating、Completed、Cancelled、Settling、Settled、Archived。
- 支持订单取消，但必须记录原因、影响金额和审批结果。
- Order Line 的客户确认价格不能直接修改。

### 8.9 操作计调执行 Operation

- 从 Order Line 生成 Operation Task。
- 任务类型至少包括确认酒店、车辆、司机、导游、餐厅、景点、出票、客户通知和其他。
- 任务记录负责人、地接社、截止时间、状态、完成时间、备注和附件。
- 状态：Pending、In Progress、Confirmed、Failed、Cancelled。
- 操作计调可以按订单、出行日期、地接社、负责人和异常状态查看任务。
- 任务失败或逾期应进入异常列表并通知负责人。

### 8.10 地接社确认 Ground Operator Confirmation

- 对每个关键资源项记录地接社最终确认的资源名称、人民币单位成本、人民币总成本、联系人、确认时间、状态、条款和证据附件。
- 状态：Pending、Confirmed、Rejected、Changed、Cancelled、Archived。
- 地接社确认成本不会修改客户确认价格，也不会覆盖 Order Line。
- 确认成本与订单成本基准不同时自动形成差异提示。
- 超过金额或比例阈值时要求原因与主管审批。
- 同一资源多次确认必须保留历史，当前生效确认需要明确标识。

### 8.11 变更单 Change Order

- 订单确认后的资源、成本、售价、行程、日期、数量、取消等变化必须创建变更单。
- Change Order 包含一条或多条 Change Order Line。
- 每条变更记录关联资源项/订单明细、变更前快照、变更后快照、成本差额、售价差额和原因。
- 状态：Draft、Pending Internal Approval、Approved、Rejected、Customer Confirmation Pending、Customer Confirmed、Applied、Cancelled。
- 涉及客户价格、权益或行程实质变化时必须取得客户确认。
- Applied 前不改变执行基准；Applied 后不可编辑，只能通过新的变更单纠正。
- 变更单不可删除，只能取消，并保留取消原因。

### 8.12 收款、付款与结算 Settlement

- 结算单从 Order、Order Line、地接社确认和已应用变更生成。
- Settlement Line 必须关联 Order Line/Itinerary Item，并保留地接社和变更来源。
- 每行展示报价成本、地接社确认成本、变更影响、实际结算成本和差异。
- 自动计算：
  - `cost_delta = actual_settlement_cost - quoted_cost`
  - `ground_operator_delta = actual_settlement_cost - supplier_confirmed_cost`
  - `profit_delta = confirmed_selling_price - actual_settlement_cost`
- 差异不为 0 时必须选择分类并填写原因；超过阈值需要审批。
- 差异分类至少包括地接社涨价、资源替换、数量变化、日期变化、操作计调录入错误、收客计调折扣、客户升级、客户取消、税费/服务费和未知。
- Settlement 状态：Draft、Pending Review、Approved、Partially Paid、Paid、Closed、Cancelled。
- 后续财务模块只记录线下客户收款和地接社付款结果及凭证，不在系统内发起、处理或回调真实资金交易。取消、部分取消、退款和坏账不属于 P0，后续版本需重新定义后再实施。
- 最终计算总客户收入、总实际成本、毛利润和毛利率。
- Closed 后不可修改；纠错使用冲销/调整记录，保留原记录。

### 8.13 审计、附件与追溯

- Audit Log 至少记录实体类型、实体 ID、动作、旧值、新值、操作人、角色、原因、时间、IP 和请求标识。
- P0 询盘关联日志至少覆盖七类操作：创建询盘、编辑询盘、创建行程（含复制为新 Draft）、编辑并保存 Draft 行程、确认下载行程 PDF、归档询盘、流失询盘。
- 日志按操作时间倒序展示；行程类日志显示行程编号和标题，流失日志显示流失原因。取消、校验失败或 PDF 仅预览未确认下载时不记录成功日志。
- 一次询盘编辑同时进入 Lost 时，分别记录“编辑询盘”和“流失询盘”。当前前端原型不记录编辑 diff，生产实现需要保存旧值、新值或结构化 diff。
- 必须审计：状态流转、版本生成、资源/价格变化、客户确认、订单创建、地接社确认、变更审批与应用、实际成本修改、结算审批、权限修改和数据导出。
- 审计日志只允许追加，不允许普通业务用户编辑和删除。
- 支持从 Settlement Line 向上追溯到变更、地接社确认、订单、报价、成本、行程资源和需求。
- 附件支持报价确认、地接社确认、发票、付款凭证、服务照片和其他证据。
- 附件保存原文件名、类型、大小、上传人、时间、业务归属和访问权限。

### 8.14 数据导入与导出

- 支持 Ground Operators、Hotels、Room Types、Vehicles、Drivers、Vehicle-Driver Bindings、Guides、Restaurants 和 Attractions 导入。
- 导入文件使用固定 sheet/表头和稳定 code。
- 每行支持 Import/Ignore；示例行默认 Ignore。
- 支持必填校验、数据类型校验、字典校验、外键校验和 code 重复校验。
- 支持 dry-run，正式导入前展示新增、更新、忽略和失败数量。
- 错误报告必须包含 sheet、行号、字段、原值和原因。
- 同一文件重复执行需要幂等，不能重复创建相同 code 数据。
- 导入文件和错误报告不得提交到 Git。
- 导出需要权限和审计，敏感字段按角色脱敏。

## 9. 状态机和版本规则

- 状态变更由后端状态机控制，禁止前端任意写入字符串。
- 每个状态明确可执行动作、所需权限、前置条件和下一状态。
- 客户确认、内部审批、锁定、应用、关闭等动作应使用专用命令/API，不能通过普通更新接口模拟。
- Quote Version 和 Costing Sheet 需要独立版本实体并保存生成时快照。Draft Itinerary 即使已生成成本核算版本仍可继续编辑，但不会反向覆盖已有快照；行程报价后如需调整，必须复制为新的独立 Itinerary。
- 锁定后的版本不得通过管理员普通编辑绕过；确需纠错时使用受审计的专用流程。
- 使用乐观锁或版本号防止多人同时覆盖。

## 10. 岗位工作台与报表

### 10.1 收客计调工作台

- 新增询盘、待跟进、超期跟进。
- 按收客计调统计询盘、合格率、报价数、成交数、成交率和 Lost 原因。
- 待客户确认报价、即将过期报价和待收款订单。
- 每单售价、预计利润和折扣异常。

### 10.2 操作计调工作台

- 待设计行程、待核成本、待确认资源。
- 今日/本周出发订单和执行任务。
- 地接社待回复、任务逾期、资源确认失败。
- 地接社确认价格异常、待处理变更和审批结果。

### 10.3 财务工作台

- 待收款、逾期应收、待付款和逾期应付。
- 待结算订单、差异订单和待审批结算。
- 报价成本/地接社确认/实际结算差异。
- 每单利润、毛利率和利润偏差。

### 10.4 管理层工作台

- 收客计调转化率、订单金额、毛利和毛利率趋势。
- 收客计调、操作计调和团队处理效率。
- 成本偏差率、变更率和未说明差异数量。
- 地接社涨价频率、确认及时率和服务评分。
- 支持按日期、收客计调、操作计调、目的地、地接社和订单状态筛选。

指标口径必须在开发前定义，尤其是成交率、操作计调错误率、地接社涨价率和利润口径。

## 11. 国际化与文档输出

- 前端至少支持中文和英文界面，使用统一 i18n 资源，不在组件内硬编码文案。
- 行程标题、每日描述、客户可见说明等支持中英文内容。
- 日期、数字、人民币金额和时区按统一规则格式化。
- 报价单和行程确认单支持选择语言，不得包含内部成本字段。
- 后端错误使用稳定错误码，前端根据错误码翻译，不能依赖后端中文字符串判断逻辑。

## 12. API 与集成约束

- 对外提供版本化 REST API，例如 `/api/v1`。
- 保留健康检查 `/api/health` 和可访问控制的 API 文档。
- 后端 API 全部重新设计，不要求兼容现有 API；新前后端以共同确认的 OpenAPI 契约为准。
- API 使用统一分页、筛选、排序、错误结构、时间格式和幂等策略。
- 旅行社联系人使用稳定 ID。询盘内创建联系人时，后端需处理同一旅行社下的重复姓名并返回最终联系人记录；新增联系人对后续询盘查询立即可见。
- 客户确认、消息回调和批量导入需要幂等键。
- P1 可集成邮件、短信、WhatsApp、微信和对象存储；每个集成必须可配置和可替换。

## 13. 非功能需求

### 13.1 安全

- 生产环境使用 HTTPS；数据库、后端管理端口不直接暴露公网。
- 密码使用可靠哈希；令牌支持过期、撤销和权限变更失效。
- `.env`、数据库、证书、密钥、客户数据和导入文件不得提交 Git。
- 文件上传限制类型和大小，进行恶意文件防护，并使用不可预测的存储键。
- 防止越权、注入、XSS、CSRF、暴力登录和敏感信息泄露。
- Docker 权限和自托管 Runner 按生产权限管理，workflow 修改权等同生产服务器权限。

### 13.2 数据一致性

- 金额使用定点数，不使用浮点数；统一按人民币存储和展示。
- 不提供外币、汇率获取、换算或锁定能力。
- 关键生成操作使用数据库事务。
- 业务状态变化、审计日志写入和 Costing/Quote 版本快照必须在同一数据库事务内完成，避免产生状态已变更但日志或版本缺失的中间状态。
- 下游实体保存必要快照，避免上游资源主数据变化影响历史订单。
- 旅行社或联系人后续修改、停用或删除，不得改变历史 Inquiry、Quote Version 和 Order 中已经保存的客户快照。
- 唯一编号、版本号和状态迁移由数据库约束与服务层共同保证。

### 13.3 性能与可用性

- 常用列表支持分页、筛选、排序和索引。
- 目标规模、并发人数、订单量、附件量需要业务确认后制定容量指标。
- 健康检查区分应用存活和依赖就绪。
- 结构化日志包含请求 ID、用户 ID、实体 ID 和错误上下文。
- 关键错误和部署失败具备告警。

### 13.4 备份与恢复

- PostgreSQL 定时备份并加密保存到独立位置。
- 明确保留周期、RPO、RTO，并定期执行恢复演练。
- 部署支持自动健康检查和回滚。
- 数据迁移、批量导入和高风险变更前创建可恢复点。

### 13.5 工程质量

- 前端统一使用 pnpm 和唯一锁文件。
- API 契约、权限、状态机、金额计算和导入逻辑必须有自动化测试。
- 核心业务流需要端到端测试。
- 数据库结构使用迁移管理，禁止生产环境手工改表后不留记录。
- 开发、测试和生产配置隔离。

## 15. 完整路线图端到端验收场景（P1 以后）

10. 财务从订单生成逐项结算，录入实际成本和差异原因。
11. 系统计算最终利润，并从结算差异下钻到酒店地接社确认与变更单。
12. 审计日志能够展示上述每个关键动作的操作人、时间、旧值、新值和原因。

## 17. 已确认决策与后续待定事项

### 17.1 已确认决策

1. P0 只服务内部员工，不上线代理商、地接社或游客门户。
2. 客户主体只支持旅行社，不支持个人客户。旅行社作为旅游资源主数据维护；询盘必须关联已启用的旅行社，并从资源库带出其编号、名称和联系信息。
3. P0 不含财务模块。后续若增加财务功能，只记录线下收付款结果，不执行真实线上资金交易。
4. 全系统只使用人民币，不提供币种选择、汇率获取、换算或锁定。
5. 任意 Itinerary Item 都可以使用自己的数量和单位；单位成本从资源库报价带出，由地接社提供时同时带出已确定的地接社。车辆 Item 可参考资源成本价填写本行程实际车费；Item 只形成内部资源成本，不维护逐 Item 对客售价。
6. P0 当前团体报价由成人团费和儿童团费组成。儿童团费固定为成人团费的 70%；单房差按各酒店房型单位成本之和的 50% 计算并作为可选附加价展示，不采集单住人数，也不自动计入团体总报价。免费名额、税费和服务费暂不建立专用模型。
7. P0 不考虑成本或售价差异审批阈值。
8. P0 的客户交付物是指定 Quote Version 生成的行程报价 PDF，不保存客户确认凭证。
9. P0 不考虑订单取消、部分取消、退款和坏账。
10. P0 不定义收客计调查看完整成本和毛利的特殊规则；按当前岗位最小必要权限实现。
11. 所有 API 重新设计，不兼容现有 API，以新的 OpenAPI 契约为准。
12. 不迁移历史业务数据和历史未完成订单，新系统从空业务库开始；资源主数据可通过标准模板初始化。
13. 酒店、餐厅、景点、导游和车辆本身不记录是否由地接社提供；该字段属于每一条资源报价，价格列表对地接社报价展示 Tag。
14. 酒店和房型是不同的资源 Item，正式报价由“酒店 + 房型 + 价格有效时间段 + 报价来源”确定；同一房型可同时存在直营报价和多个地接社报价，每条报价最多关联一个地接社。
15. 资源报价只受时间段（如淡季、旺季）影响，不考虑含早/不含早等其他报价维度。
16. 添加资源报价时即确定报价来源；若由地接社提供，同时确定地接社。行程必须选择具体报价记录，不得只选择资源后另行指定价格或地接社。
17. 仅资源主管可以维护资源库报价。收客计调和操作计调不得修改资源库价格；车辆 Item 的实际车费允许在所选车辆资源成本价基础上手工填写，并必须保留参考成本价及变更审计。地接社报价变化时仍由资源主管修改并留下审计记录。
18. Draft 行程的所有信息均可修改；行程报价后如需调整，必须复制为新的独立 Itinerary。
19. 默认计价单位为：酒店 1 间夜、景点 1 人次、车辆 1 辆/天、餐厅按人计价 1 人/餐或整桌计价 1 桌、导游 1 人/天。
20. 金额统一保留两位小数；除车辆实际车费外，不提供针对单个行程 Item 临时增减资源报价的常规功能。
21. 创建询盘时收客计调负责人非必填，操作计调必须指定；询盘状态按 New、Planning、Quoted、Lost 流转，Archived 作为归档状态。
22. Lost 询盘只可查看；Archived 询盘及其已有行程只可查看，行程管理中不得新增、复制、编辑行程或生成新的报价 PDF。
23. 一个旅行社维护一个统一邮箱和多个联系人；联系人只保存姓名和电话，不设置部门。旅行社与联系人使用左右主从页面分别维护。
24. Inquiry 联系人从所选旅行社全部联系人中选择；没有目标人员时可直接新增并同步回旅行社，Inquiry 邮箱始终固定使用旅行社邮箱。
25. Draft 保存、PDF 确认下载和七类询盘关联操作分别记录明确日志；生产环境的日志必须由后端在业务事务成功后写入不可变 Audit Log。

### 17.2 后续待定事项

以下事项不阻塞 P0 核心数据模型，但应在对应功能开发前确认：

1. PDF 的公司模板、Logo、页眉页脚、联系方式、法律条款和语言版本。
2. P1 地接社确认是否允许多轮报价和多候选地接社，以及生效版本规则。
3. P1 取消、退款、坏账、审批和岗位成本权限的完整规则。
4. 管理层指标的正式口径，特别是成交率、操作计调错误率和地接社涨价率。
5. 真实完整业务案例及现有报价单样例（待业务方后续提供）。

## 18. 明确不应发生的实现

- 不允许直接编辑或删除已确认报价、已生成订单、已应用变更和已关闭结算。
- 不允许用一个总金额代替逐项成本和结算。
- 不允许把全部行程只写在一个富文本描述中而不拆资源项。
- 不允许把资源名称作为跨表唯一关联键。
- 不允许让前端自行计算并决定最终财务结果，后端必须重新校验。
- 不允许把权限控制、状态机或金额规则只写在前端。
- 不允许为赶进度把 P2 电商/分销功能混入核心 ERP 模型。
- 不允许前后端在没有共同确认新 OpenAPI 契约的情况下各自实现接口。
